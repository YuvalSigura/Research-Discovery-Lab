# GPT: primary-source evidence audit of four contrasting research forms

Reviewed 2026-10-16 against public author pages. This is a deeper follow-up to previous 109-source bounded reviews. **14 candidate X→Y transitions**, not 14 verified historical decision snapshots. All questions below are analyst phrasings (not historical quotations); author motive/time remain UNKNOWN except where source states it. No external reproduction, rights clearance, or independent curation. Raw exploits are not reproduced.

## Why these four
These cases force very different kinds of investigation intelligence: measurement discriminator (026); experimental harness semantics (094); missed-detection postmortem (095); narrow negative-result workflow (107). Do not force them into vulnerability-discovery diaries.

## SRC-000026 — Beware the false false-positive — request smuggling vs pipelining

Original: https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling
Form: methodological discriminator; false-positive adjudication. Lineage: James Kettle HTTP smuggling methodology; not a single original exploit discovery

### Candidate transition T1 — Connection reuse false-positives; HTTP/1 connection reuse

- **X:** A surprising paired HTTP response is observed under reused client connections.
- **Question (analyst):** Does this imply a front-end/back-end message-boundary discrepancy or ordinary client/server request pipelining?
- **Experiment/analysis:** Compare behavior without connection reuse; inspect raw request stream and response framing.
- **Source-reported observation:** Author demonstrates a response artifact that is merely a desync between tester client and target, with no back-end tier at all.
- **Y:** The originally alarming observation is insufficient evidence of request smuggling.
- **Basis:** author_demonstrated_example
- **Incorrect inference to block:** A security-looking response is not vulnerability proof; preserved client assumptions matter.

### Candidate transition T2 — Connection-locked request smuggling

- **X:** The signal disappears when ordinary connection reuse is disabled.
- **Question (analyst):** Should the hypothesis be discarded, or is connection locking a real precondition in this deployment?
- **Experiment/analysis:** Distinguish connection-locked smuggling from false positives using an independent request-provenance discriminator.
- **Source-reported observation:** Author describes valid connection-locked variants that require client reuse; a blanket no-reuse rejection is unsound.
- **Y:** Maintain competing hypotheses and seek an independent discriminator plus evidence of real impact.
- **Basis:** author_methodological_explanation
- **Incorrect inference to block:** A test designed to remove false positives can itself produce false negatives.

### Candidate transition T3 — Connection state attacks; Client-side desync attacks

- **X:** Connection-dependent anomaly may not fit the initial vulnerability label.
- **Question (analyst):** Could connection state or client-driven behavior explain the effect better?
- **Experiment/analysis:** Reclassify based on how the behavior arises and whether victim-accessible prerequisites exist.
- **Source-reported observation:** Article documents neighboring vulnerability classes with different necessary conditions.
- **Y:** Investigative question becomes taxonomy and precondition disambiguation rather than forcing the original class.
- **Basis:** author_taxonomic_analysis
- **Incorrect inference to block:** Multiple superficially identical observations do not prove the same mechanism.

## SRC-000094 — Fuzzing an API with DeepState (Part 2)

Original: https://blog.trailofbits.com/2019/01/23/fuzzing-an-api-with-deepstate-part-2/
Form: comparative experimental-method study; mutation testing. Lineage: Alex Groce DeepState red-black-tree fuzzer evaluation

### Candidate transition T1 — Mutation Testing

- **X:** One hand-inserted bug is too weak a basis to compare testing approaches.
- **Question (analyst):** Can a larger repeatable set of controlled program mutations reveal comparative strengths and blind spots?
- **Experiment/analysis:** Generate 2,602 mutants; filter to 1,120 compilable and compare detection under matched time budgets.
- **Source-reported observation:** Under 60-second tests the author reports DeepState and libFuzzer each kill 797 mutants, while the raw fuzzer kills 822.
- **Y:** A reproducible quantitative discrepancy appears that requires causal explanation.
- **Basis:** author_reported_experiment
- **Incorrect inference to block:** Mutation-test count depends on test harness and budget; invalid mutants must be excluded.

### Candidate transition T2 — There ain’t no such thing as a free lunch (or is there?)

- **X:** Raw fuzzer kills 25 additional mutants; naive inference is throughput superiority.
- **Question (analyst):** Is the shortfall due to speed, or does the forked execution environment change the observable program behavior?
- **Experiment/analysis:** Inspect the 25 remaining mutants, identify pointer comparison mutations, compare forking against persistent process execution.
- **Source-reported observation:** Author reports the difference was due to changed address-allocation history under forking; longer nonforking libFuzzer catches them.
- **Y:** Explanation shifts from candidate fuzzer quality to test-environment semantics.
- **Basis:** author_explicit_causal_experiment
- **Incorrect inference to block:** More time does not resolve environmental impossibility within a fixed harness.

### Candidate transition T3 — There ain’t no such thing as a free lunch (or is there?)

- **X:** Nonforking configuration can reveal previously missed mutant outcomes.
- **Question (analyst):** Does detecting a bug suffice for reproducible minimal test preservation?
- **Experiment/analysis:** Add --no_fork support and assess whether a saved test replays with same address/allocator history.
- **Source-reported observation:** Author states nonforking detects these cases but does not yield a good saved reproducible test because failure depends on allocator history.
- **Y:** Detection success separated from proof/reproduction quality.
- **Basis:** author_reported_followup
- **Incorrect inference to block:** A detection without replayable evidence requires a distinct status.

### Candidate transition T4 — Examining the Mutants

- **X:** Hundreds of mutants remain undetected even after additional fuzzing.
- **Question (analyst):** Are these real detection misses, equivalent mutants, untested code, or irrelevant mutations?
- **Experiment/analysis:** Inspect a random sample of remaining 298; compare changed semantics with exercised APIs.
- **Source-reported observation:** Author observes examples in comments, excluded printing routines and semantically inert sentinel values.
- **Y:** Unkilled counts are not automatically failures; denominator meaning requires adversarial review.
- **Basis:** author_sample_analysis
- **Incorrect inference to block:** Absence of kill is not evidence that all unseen mutants represent exploitable missed bugs.

## SRC-000095 — This shouldn't have happened — BigSig postmortem

Original: https://projectzero.google/2021/12/this-shouldnt-have-happened.html
Form: discovery narrative plus retrospective missed-detection postmortem. Lineage: Tavis Ormandy NSS BigSig 2021; separated from previous fuzzers' unseen decisions

### Candidate transition T1 — How did I find the bug?; Stack Coverage; Object Isolation

- **X:** Conventional edge/block coverage can discard semantically distinct entry paths during minimization; the researcher is experimenting with new coverage signals.
- **Question (analyst):** Can stack-level coverage combined with isolation of structured input records reveal paths missed under ordinary corpus minimization?
- **Experiment/analysis:** Develop a stack-monitoring library and ASN.1 object isolation for a coverage-guided NSS fuzzer.
- **Source-reported observation:** The researcher reports discovery of BigSig while evaluating the new fuzzer.
- **Y:** An actual vulnerability is discovered, but the value of the new strategy remains causally unresolved.
- **Basis:** author_reported_discovery
- **Incorrect inference to block:** The author explicitly says he cannot establish this specific bug would not have been found by rudimentary fuzzing.

### Candidate transition T2 — Lessons Learned; Issue #1 Missing end-to-end testing

- **X:** Existing fuzzers cover parsing code yet the real flaw escaped.
- **Question (analyst):** Do fuzzers generate objects that they never pass to the vulnerable downstream signature-verification API?
- **Experiment/analysis:** Review QuickDER harness and compare decoded-object lifetime with end-to-end certificate-verification flow.
- **Source-reported observation:** Published harness decodes then destroys objects without exercising signature verification.
- **Y:** A specific missing end-to-end edge explains why this harness cannot detect this bug.
- **Basis:** author_postmortem_code_inspection
- **Incorrect inference to block:** Coverage on one parsing stage does not establish coverage of downstream use.

### Candidate transition T3 — Lessons Learned; Issue #2 Arbitrary size limits

- **X:** Some harnesses exercise relevant APIs but not attacker-controlled length extremes.
- **Question (analyst):** Does an artificial 10,000-byte fuzz-input cap exclude the inputs needed to trigger the bug?
- **Experiment/analysis:** Inspect fuzz configuration and contrast cap with actual protocol/library object limits.
- **Source-reported observation:** Author identifies a 10,000-byte fuzzer cap narrower than NSS-accepted objects and recommends revisiting the bound.
- **Y:** Size-limit coverage becomes a separate explanation of missed detection.
- **Basis:** author_postmortem_configuration_inspection
- **Incorrect inference to block:** A safe-looking arbitrary budget bound may remove the relevant input space.

### Candidate transition T4 — Lessons Learned; Issue #3 Misleading metrics

- **X:** Project-level code coverage suggests vulnerable routines are well exercised.
- **Question (analyst):** Can coverage from a different harness make a target routine appear tested even when attacker-influenced arguments are static?
- **Experiment/analysis:** Inspect per-harness instrumentation and fixed certificate arguments.
- **Source-reported observation:** Author finds aggregate oss-fuzz coverage includes executions driven by fixed certificate inputs.
- **Y:** Harness-specific reachability becomes the relevant metric; aggregate project coverage is a false assurance.
- **Basis:** author_postmortem_coverage_analysis
- **Incorrect inference to block:** A line being hit does not imply the risky input degree of freedom was explored.

## SRC-000107 — Taming 2,500 compiler warnings with CodeQL — OpenVPN2

Original: https://blog.trailofbits.com/2025/09/25/taming-2500-compiler-warnings-with-codeql-an-openvpn2-case-study/
Form: iterative static analysis and bounded negative security review. Lineage: Trail of Bits OpenVPN2 implicit integer conversion audit 2025

### Candidate transition T1 — Building a practical CodeQL query; Step 0: Learn from existing CodeQL queries

- **X:** 2,500+ compiler conversion warnings create unaffordable manual review; existing query classes are either incomplete or too noisy.
- **Question (analyst):** Which conversion semantics are relevant to security, and how should a query encode them?
- **Experiment/analysis:** Review three prior CodeQL queries; build more general detection logic.
- **Source-reported observation:** Published query returns >7,000 initial results, then filtered to 5,725 security-relevant candidate conversions.
- **Y:** The investigation transitions from raw warnings to an explicit hypothesis about dangerous conversion semantics.
- **Basis:** author_reported_design
- **Incorrect inference to block:** Initial compiler-warning count and initial broad CodeQL result count measure different criteria.

### Candidate transition T2 — Step 2: Eliminate provably safe constants; Step 3: Apply range analysis

- **X:** Thousands of conversion expressions remain after the broad semantic filter.
- **Question (analyst):** Which candidates are provably within safe numeric ranges under static constraints?
- **Experiment/analysis:** Introduce constant bounds and progressively more precise range analysis, measuring runtime/precision tradeoff.
- **Source-reported observation:** Published counts decline to 1,017 and then 435 with more precise analysis.
- **Y:** Hypothesis space shrinks under explicit proof obligations rather than heuristically discarding all warnings.
- **Basis:** author_reported_iterative_analysis
- **Incorrect inference to block:** Filtered results are not separate refuted vulnerabilities.

### Candidate transition T3 — Step 4: Model codebase-specific knowledge; Step 5: Focus on user-controlled inputs

- **X:** Remaining conversions are syntactically suspicious but many involve safe library-level bounds or no untrusted input.
- **Question (analyst):** Which remaining conversion candidates can be influenced by attacker-controlled values?
- **Experiment/analysis:** Build OpenVPN2/standard/OpenSSL function models, then apply data-flow source filtering.
- **Source-reported observation:** Published count falls from 254 to 20 manually reviewed candidates.
- **Y:** Manual inspection is now tractable and concentrated on attacker-influence semantics.
- **Basis:** author_reported_query_refinement
- **Incorrect inference to block:** Models and taint assumptions can cause false negatives and require independent correctness checks.

### Candidate transition T4 — Step 5: Focus on user-controlled inputs

- **X:** 20 highest-priority residual conversion candidates remain.
- **Question (analyst):** Do any of the residual cases create exploitable security failures in this codebase?
- **Experiment/analysis:** Manual review of 20 cases.
- **Source-reported observation:** Authors report none exploitable in the tested OpenVPN2 context.
- **Y:** A bounded no-exploitable-findings conclusion and a reusable analysis artifact.
- **Basis:** author_reported_negative_review
- **Incorrect inference to block:** Not proof no conversion vulnerabilities exist in all configurations or that query filtering was complete.

## Cross-case falsification and training risks

- These are explicitly **heterogeneous** cases; a postmortem causal explanation (095) is not the original discoverer's contemporaneous decision (nor the undocumented earlier fuzzers' mental model).
- A test can fail because of instrumentation, environment, input constraints, and denominator choice, while the original vulnerability hypothesis remains plausible (026, 094, 095).
- Systematic filtering with **zero exploitable findings** can still be successful research when the methods, reachable inputs and negative scope are recorded (107).
- Do not automatically fine-tune a next-step recommender with a finished article, because the observed Y is written after X. Only contemporaneous known-at artifacts would make a true historical predecision supervision example.
- For routine-versus-open-exploration analysis, separate what the publisher says about planning from what the analyst wants a future system to do.
